1. Propósito del Proyecto de Aula y Marco de Negocio

El Proyecto de Aula busca integrar los conocimientos y prácticas trabajados en la asignatura de Ingeniería de Software mediante el desarrollo incremental de una solución de software a un problema real y representativo de la industria. El proyecto se ejecutó durante el segundo y tercer corte evaluativo, consolidando evidencias completas de análisis, diseño, construcción, pruebas en base de datos real, gestión ágil del trabajo y liberación del Producto Mínimo Viable (MVP).

1.1. Descripción del Problema

Encontrar un mecánico de confianza, cotizar el repuesto exacto y llevar un registro organizado de las modificaciones suele ser un desafío constante para los propietarios de vehículos en Colombia. Actualmente, la información se encuentra fragmentada, los precios de las piezas varían sin control y, en muchas ocasiones, el usuario carece de certeza sobre la compatibilidad de un componente o la reputación real del taller al que acude.

1.2. Solución Propuesta (Alcance del MVP)

Motrick es una plataforma web full-stack diseñada para centralizar la gestión vehicular. Para garantizar la viabilidad dentro del tiempo disponible, el alcance del MVP se estructura en tres módulos clave:

  • Directorio de Servicios Especializados: Catálogo de mecánicos y talleres filtrable por especialidad técnica, que incluye cálculo de calificación promedio y solicitud de verificación formal de talleres.
  • Buscador y Catálogo de Repuestos: Módulo de consulta categorizado y filtrable por modelo vehicular con validación de compatibilidad técnica.
  • Bitácora de Mantenimiento y Garaje Digital: Espacio donde el propietario registra los servicios preventivos y correctivos, controlando odómetro, piezas actualizadas, costos y fechas de vencimiento legal de SOAT y revisión técnico-mecánica.

1.3. Alcance y Restricciones Tecnológicas

  • Persistencia de Datos: El sistema opera conectado a una base de datos relacional PostgreSQL alojada en Supabase Cloud, implementando políticas de seguridad a nivel de fila (Row Level Security - RLS).
  • Simulación de Pasarela de Pagos (RNF-03): El flujo de compra de repuestos implementa una maqueta interactiva en 4 pasos (Resumen, Tarjeta con animación 3D, Procesamiento y Comprobante) para evaluar la experiencia de usuario (UX) sin procesar cobros financieros reales.

1.4. Arquitectura y Tecnologías

La arquitectura del sistema se fundamenta en un ecosistema unificado basado en JavaScript y TypeScript estricto:

  • Framework Full-Stack: Next.js 14 con arquitectura App Router, utilizando React 18 para el renderizado interactivo y Tailwind CSS para un diseño responsivo con soporte nativo de modo oscuro/claro.
  • Backend y Persistencia: Supabase (BaaS) sobre PostgreSQL 15, garantizando integridad referencial, restricciones de dominio CHECK y autenticación.

1.5. Modelo de Negocio y Deslinde de Responsabilidad Legal (Ley 1480 de 2011)

Motrick implementa un modelo de monetización B2B sustentado en membresías de visibilidad para talleres mecánicos y pauta publicitaria nativa, descartando expresamente el cobro de comisiones sobre reparaciones mecánicas.

Prevención de Solidaridad Jurídica

De acuerdo con el Artículo 53 de la Ley 1480 de 2011 (Estatuto del Consumidor en Colombia), la plataforma califica como portal de contacto e intermediación informativa. Si Motrick recaudara el valor del servicio de mano de obra o comisionara sobre el arreglo mecánico, la Superintendencia de Industria y Comercio (SIC) la consideraría prestador solidario, debiendo responder económicamente ante fallas mecánicas, averías colaterales o garantías no atendidas por el taller.

Al limitar los ingresos al canon de visibilidad y verificación documental, la relación contractual por el servicio automotriz se suscribe directa y exclusivamente entre el propietario del vehículo y el taller mecánico contratado.

Cláusula de Deslinde en Términos y Condiciones:
"Motrick opera bajo la figura de portal de contacto (Art. 53, Ley 1480 de 2011). La plataforma no ejecuta diagnósticos mecánicos, no provee mano de obra ni actúa como garante solidario de los trabajos realizados por los talleres listados. La contratación de servicios automotrices, su calidad y cumplimiento de garantías recaen exclusivamente en el establecimiento seleccionado por el usuario."

1.5.2. Publicidad Nativa Contextual y Política de Brand Safety (RNF-04)

Como línea secundaria de sostenimiento, se habilitan espacios pasivos en los márgenes y zonas blancas de la interfaz, alineados con los Artículos 29 y 30 de la Ley 1480 de 2011 (protección contra publicidad engañosa):

  • Relevancia temático-vehicular: Solo se admiten anunciantes de servicios afines (SOAT digital, revisión técnico-mecánica en Centros CDA aliados, escáneres OBD2 Bluetooth y telepeaje).
  • Cero intrusión (UX): Se vetan pop-ups, modales bloqueantes o banners con sonido, garantizando cero desplazamiento visual (Cumulative Layout Shift = 0).
  • Seguridad de marca (Brand Safety): Quedan prohibidos juegos móviles, apuestas deportivas, esquemas de inversión y contenido adulto (+18). Toda inserción cuenta con el distintivo gráfico visible y obligatorio "Patrocinado".

3. Técnicas de Elicitación Aplicadas

Para fundamentar técnicamente los módulos del sistema, se aplicaron tres metodologías formales de levantamiento de requisitos:

3.1. Benchmarking (Análisis de Soluciones Similares)

Se analizaron aplicaciones líderes en gestión y servicios automotrices (Drivvo, Autolab y MercadoLibre Repuestos). Conclusión: las aplicaciones existentes resuelven problemas de forma fragmentada. La ventaja competitiva de Motrick radica en centralizar en una sola plataforma el directorio confiable, el catálogo compatible y la bitácora técnica.

3.2. Encuesta a Usuarios Finales (Propietarios de Vehículos)

Se diseñó e implementó un formulario estructurado aplicado a 49 propietarios de vehículos en Colombia para cuantificar las dificultades cotidianas en el mantenimiento automotriz.

3.3. Revisión Documental (Informes de la Industria y Gremios)

Se analizaron reportes de la American Automobile Association (AAA, 2016), estudios de McKinsey & Company (2018) sobre el mercado de postventa automotriz, e informes gremiales de ASOPARTES y FENALCO (2023) sobre informalidad y compra desinformada de autopartes en Colombia.

4.2. Resultados Consolidados de la Encuesta a 49 Usuarios

El instrumento digital evidenció datos contundentes sobre los hábitos de los conductores:

  • Búsqueda de Mecánicos: El 91.8% depende exclusivamente de la recomendación informal ("boca a boca"), demostrando la ausencia de herramientas digitales confiables.
  • Filtros por Especialidad y Reseñas: El 98.0% consideró "Muy útil" o "Útil" consultar valoraciones y filtrar mecánicos por especialidad antes de acudir.
  • Dificultad en Repuestos: El 53.1% manifestó que su mayor temor al comprar autopartes es "Tener certeza de la compatibilidad con mi vehículo".
  • Control de Historial: El 75.5% no lleva ningún registro o guarda facturas sueltas en la guantera con riesgo de pérdida.
  • Aceptación de la Propuesta: El 100% de los encuestados afirmó que usaría una plataforma que centralice talleres, repuestos compatibles y bitácora digital.

4.3. Hallazgos de la Revisión Documental del Sector

  • Desconfianza Estructural (Estudio AAA): Dos tercios de los conductores desconfían de los talleres por temor a cobros inflados. Motrick mitiga esto mediante el sistema de valoraciones auditadas y el canal de verificación documental (RF-05).
  • Incompatibilidad de Autopartes (ASOPARTES): La compra desinformada de repuestos paraliza los talleres. Motrick soluciona esto categorizando piezas compatibles con el modelo exacto (RF-04).
  • Asimetría Informativa: La ausencia de bitácora provoca diagnósticos redundantes y costosos. Motrick transfiere el control digital del historial al usuario (RF-01).

6. Priorización de Requerimientos y Alcance Funcional

Aplicando los principios de la metodología Feature-Driven Development (FDD), los requerimientos se clasificaron en tres niveles de entrega:

  • Prioridad Alta (Obligatorios para el MVP): RF-01 (Bitácora), RF-02 (Directorio), RF-04 (Repuestos compatibles), RNF-01 (Next.js) y RNF-02 (Supabase).
  • Prioridad Media (Valor agregado indispensable): RF-03 (Valoraciones), RF-05 (Verificación de talleres), RNF-03 (Checkout simulado) y RNF-04 (Pauta nativa contextual).
  • Prioridad Baja (Alcance futuro post-MVP): Conexión en tiempo real con inventarios de concesionarios y pasarela bancaria real con PSE / tarjeta de crédito.
Cumplimiento de Alcance: Al cierre de la iteración final, el 100% de los requerimientos de Prioridad Alta y Media se encuentran completamente desarrollados, integrados y probados.

9.1. Reglas de Negocio Acordadas y Datos Semilla

9.3. Registro y Corrección de Defectos en el Código Fuente

Defecto D1: Validación de Kilometraje en Bitácora (RF-01, Regla R1)

Condición: Detectado en el caso T02 al verificar que el modal permitía registrar kilometrajes inferiores al odómetro actual registrado en el vehículo (por ejemplo, registrar 45.000 km cuando el auto ya registraba 48.230 km), generando inconsistencia cronológica.

Corrección Aplicada: En src/app/bitacora/page.tsx, dentro de la función submit() de MaintenanceDialog, se añadió la guarda previa que bloquea la mutación hacia Supabase:

Código Antes (Vulnerable a inconsistencia):
const kmN = Number(f.km);
if (!f.title.trim()) return setErr("Describe el servicio.");
if (!kmN) return setErr("Ingresa el kilometraje.");
setSaving(true); 		Código Corregido (Con guarda de odómetro):
const kmN = Number(f.km);
if (!f.title.trim()) return setErr("Describe el servicio.");
if (!kmN) return setErr("Ingresa el kilometraje.");
if (kmN < activeVehicle.odometer) {
  toast.error(`El kilometraje (${kmN} km) no puede ser inferior al actual (${activeVehicle.odometer} km).`);
  return;
}
setSaving(true);

Defecto D2: Validación Estricta de Tarjeta y CVV en Checkout (RNF-03, Regla R5)

Condición: Detectado en el caso T07 al comprobar que el botón para avanzar a la animación de pago procesaba la acción con tarjetas incompletas de 15 dígitos o CVVs de 2 dígitos.

Corrección Aplicada: En src/components/motrick/Checkout.tsx, se integró el controlador handleProceedToPayment() que sanitiza espacios y valida la longitud estricta de ambos campos:

Código Antes (Validación pasiva):
<Button
  variant="cta"
  onClick={() => { setTouched(true); if (valid) setStep(2); }}
>
  Pagar {cop(total)}
</Button> 		Código Corregido (Validación estricta con toast):
const handleProceedToPayment = () => {
  setTouched(true);
  const raw = card.number.replace(/\s/g, "");
  if (raw.length !== 16 || card.cvv.trim().length !== 3) {
    toast.error("Ingrese tarjeta de 16 dígitos y CVV de 3 dígitos.");
    return;
  }
  if (!valid) return;
  setStep(2);
};
